# Traffic forecasting — methodology

## Purpose

This feature demonstrates a **complete, replaceable ML integration**, not
predictive performance:

* dataset validation and documented lineage;
* reproducible preprocessing (one code path, train and inference);
* a **versioned model artifact** that records the source-code and dataset
  hashes that produced it;
* **inference-only** API serving (it never trains on a request);
* load-time compatibility checks and structured errors;
* frontend visualisation with honest limitations.

The bundled models are trained on a fixed ~2-week 2022 sample only to exercise
that contract end to end. **With real client data or a client-provided model,
the same pipeline retrains a replacement bundle and the same API serves it, with
no application changes.**

Every number in this document is regenerated by the commands in
[§8](#8-reproducible-commands); nothing is hand-entered.

## 1. Data and lineage

### Source of truth

`back-end/ml/data/passages.csv` — a verbatim export of the seeded `Passages`
table joined to `Toll`, and `back-end/ml/data/tolls.csv` — the seeded `Toll`
table. Both are regenerated with a documented `mysql` command
(`back-end/ml/README.md`); `python -m ml.validate_data` re-checks the CSV against
the live seed database when one is reachable and **matched exactly** at the time
of writing (`db=1002`, `csv=1002`, same date range).

```
db/init/02-data.sql  ──►  Passages ⨝ Toll  ──►  ml/data/passages.csv
                                              ├─►  volume table: (station, date) → count   (0-filled grid)
                                              └─►  hourly table: (date, hour 0-23) → count → argmax = peak hour
                                                          │
                                                   chronological split
                                                          │
                                              ml/train_all  ──►  ml/artifacts/v2/{volume,peak}/<OP>.joblib
                                                          │
                                              ml/evaluate_all  ──►  ml/evaluation/v2/metrics.json
                                                          │
                                              ml/infer  ◄── API (/api/forecast, /api/peak_hour)
```

### What the sample contains

| | |
|---|---|
| Rows (passages) | **1 002** |
| Duplicate rows | 1 (identical timestamp/station/tag/charge — kept, not synthesised away) |
| Unique dates | **15** (2021‑12‑31 → 2022‑01‑14, ~2 weeks) |
| Sample frequency | irregular event log, minute-resolution timestamps |
| Toll stations total / with ≥1 passage | 253 / **137** |
| Operators | AM, EG, GE, KO, MO, NAO, NO, OO |
| Passages per operator | NAO 235, EG 223, AM 132, NO 132, OO 119, KO 106, MO 41, **GE 14** |
| Missing values | none |
| Multiple stations per date | yes — every date has passages at many stations |

**Passage-volume target** (`passages per station-day`, full station × date grid):
zero fraction **0.69 – 0.92** per operator, mean **0.15 – 0.47**, max 2 – 4.
Per-station daily counts are essentially binary noise on this sample.

**Peak-hour target** (hour with the most passages per date): 7 – 12 of the 15
dates per operator have **two or more hours tied** for the peak (ties broken to
the earliest hour). GE averages **0.9 passages/day** total. The observed peak
hours cluster in 00:00 – 02:00, an artefact of how the sample was generated.

### Reproducibility of the *previous* models — NOT reproducible

The committed legacy artifacts (`back-end/models_passages/*.pkl`,
`back-end/models_peak_hours/*.pkl`) **cannot be reproduced** from the seeded data.
The legacy training tables (`back-end/ml/training_data/*.csv`,
`back-end/ml/training_data_peak_hours/*.csv`) do not match `passages.csv` or
`db/init/02-data.sql` — different dates and different counts — and there are at
least three different passage datasets in the repo
(`back-end/uploads/passages.csv` is April–May 2022;
`Database_mysql/useful_scripts/passes-sample.csv` is Jan 2022; the seed is a
third variant). The exact origin of the legacy training tables is undocumented.

**The v2 pipeline is built only from `ml/data/passages.csv`.** The legacy tables
and `.pkl` files are kept for now as evidence and as a fallback until v2 is
accepted; they are cleanup candidates (see `docs/TECH_DEBT.md`).

## 2. The previous approach — recorded before replacement

`python -m ml.evaluate_legacy` → `back-end/ml/evaluation/legacy/metrics.json`.
It does **not** touch the legacy `.pkl` files. It re-runs the legacy methodology
on the seeded data and also scores the shipped `.pkl` artifacts.

Legacy feature sets:

* passage volume: `[tollID (LabelEncoded), Year, Month, Day, DayOfYear]`, trained
  on the **observed (non-zero) station-days only**;
* peak hour: `[day_of_week, month, year]`, regressing `hour_of_day` **directly**.

| | random 80/20 (as shipped) | chronological split |
|---|---|---|
| **Volume** macro MAE | 0.47 | 0.51 |
| **Volume** macro sMAPE | 33 % | 34 % |
| **Peak hour** macro MAE (hours) | 6.3 | 6.9 |
| **Peak hour** exact-hour accuracy | ~0 – 11 % | ~0 – 14 % |
| **Peak hour** within-1 (circular) | ~0 – 33 % | ~0 – 25 % |

Shipped `.pkl` volume models on the chronological test dates: MAE 0.32 – 0.54.

> **These figures are not comparable with the v2 numbers in §6.** The target
> populations differ (legacy volume = non-zero station-days only; v2 = the full
> station × date grid the API predicts) and the evaluation differs. They are here
> to document *methodology problems*, not to compare accuracy.

**What was wrong with the methodology:**

1. **Random `train_test_split`** puts the same calendar date in train and test
   through different stations — optimistic leakage.
2. **Encoder mismatch.** `train.py` fits a `LabelEncoder` on `tollID` and never
   saves it; `predict.py` looks for a `label_encoder.pkl` that never exists and
   silently fits a **fresh** encoder on the request's stations, in
   `pandas.unique()` order — so the integer a station maps to at inference is
   unrelated to training. The shipped models predict on scrambled station codes.
3. **Direct hour regression.** Predicting a real number in [0, 23] treats 23:00
   and 00:00 as ~23 apart, produces fractional "peak hours" (`14.26`), and is
   evaluated with plain MAE — meaningless on a circular quantity.
4. Trained on **non-zero station-days only**, so the model never sees that most
   station-days are 0.

v2 fixes each of these. Whether v2's numbers are "better" is not a claim this
document makes — the datasets, targets and evaluation populations are different.

## 3. Chronological split

`chronological_split()`. The unit is the **unique date**, never the row.

| split | dates | range |
|---|---|---|
| train | 11 | 2021‑12‑31 → 2022‑01‑10 |
| validation | 2 | 2022‑01‑11 → 2022‑01‑12 |
| test | 2 | 2022‑01‑13 → 2022‑01‑14 |

Target proportions ~70 / 15 / 15 of unique dates. With only 15 dates this is
statistically threadbare — **test = 2 dates** — and every downstream number is
reported with that caveat. `assert_no_leakage()` (checked in `ml.tests`) enforces:

* `max(train) < min(val) < max(val) < min(test)`;
* no date in more than one split;
* no operator has rows for the same date in two splits.

The deployed model is fit on **train + val**. Hyper-parameters are fixed, not
searched (see §5), so **no model selection or tuning uses the test data**.
`ml.evaluate_all` scores the shipped artifacts on the held-out dates and is
**rerun unchanged for reproducibility** — the same command produces the same
numbers. An expanding-window rolling-origin MAE over the train+val period is
recorded in each artifact's metadata as a sanity check.

No target-derived feature uses future data: features are calendar-only
(and station identity for volume), all computable for an arbitrary requested date.

## 4. Baselines — sanity checks

The naive baselines exist to answer one question: *is the model doing anything a
mean would not?* They are **not a target to beat**, and no tuning or extra
experiment was run to select or beat one.

A baseline may only use information available at prediction time. The API is
given a future date and nothing else, so **"last observed value"** and
**"7-day seasonal naive"** are *not applicable* (no history at the requested
date; the sample has no full weekly cycle) — recorded as such, not approximated.

| task | baselines |
|---|---|
| passage volume | `global_mean` (train+val mean), `per_station_mean` |
| peak hour | `global_peak_hour_mode`, `day_of_week_peak_hour_mode` |

Metrics: **MAE**, **RMSE**, **sMAPE** (zero-safe), sample count. R² is not used as
a headline (unstable on this target). For peak hour: **exact-hour accuracy**,
**within-1-hour accuracy** and **mean circular absolute error**, using
`circular_distance = min(|p−a|, 24−|p−a|)`.

## 5. Models (v2)

Both tasks: `RandomForestRegressor(n_estimators=120, max_depth=6,
min_samples_leaf=3, random_state=42)`. Small and shallow **on purpose** — the
per-station / per-hour signal here is near-noise, so deep trees only overfit and
bloat the artifact. Hyper-parameters are **fixed, not searched**. The architecture
is kept as-is unless a correctness bug forces a minimal change.

* **Passage volume** — one `VolumeModel` per operator. Features
  `[station_code, day_of_week, month, day_of_year, is_weekend, dow_sin, dow_cos,
  doy_sin, doy_cos]`. The fitted object **carries its own station vocabulary**;
  `ml.features.volume_matrix` builds the identical matrix at train and inference
  time (one code path). Unknown station id → explicit fallback to that station's
  training mean, else the operator global mean. Predictions are clipped to
  ≥ 0 and checked finite.

* **Peak hour** — one `PeakModel` per operator. It models the **expected passage
  count for each (date, hour)** from `[hour, hour_sin, hour_cos, calendar…]`,
  predicts all 24 hours for a requested date, and returns `argmax` as an
  **integer hour 0–23**. No fractional output, no confidence interval (the sample
  cannot justify one).

Artifacts are self-contained `joblib` bundles (preprocessing + estimator +
metadata), `compress=3`. Total size **~1.3 MB** for all 16 (8 operators × 2
tasks). See §7.

## 6. Results (v2, held-out test)

`python -m ml.evaluate_all` → `back-end/ml/evaluation/v2/metrics.json`
(+ `per_company_*.csv`, `predictions_*_test.csv`, `plots/`). **Test = 2 dates —
this shows the integration works end to end; it is not evidence of predictive
skill.** The baseline column is a **sanity check**, not a verdict.

### Passage volume — MAE per station-day

| operator | model MAE (full grid) | mean baseline MAE (sanity check) | model MAE (non-zero actuals only) |
|---|---|---|---|
| AM | 0.219 | per_station_mean 0.176 | 0.50 |
| EG | 0.273 | per_station_mean 0.276 | 0.79 |
| GE | 0.767 | global_mean 0.750 | 1.30 |
| KO | 0.247 | per_station_mean 0.238 | 0.45 |
| MO | 0.184 | per_station_mean 0.239 | 1.22 |
| NAO | 0.560 | per_station_mean 0.558 | 1.02 |
| NO | 0.268 | per_station_mean 0.284 | 0.96 |
| OO | 0.286 | per_station_mean 0.260 | 0.66 |

Macro MAE **0.35**, RMSE **0.57**. The model tracks the per-station mean closely
in both directions — on a sample this small that is all one should expect. sMAPE
(~147 %) is uninformative here: the target is zero-inflated (77 – 92 % zeros on
the test dates), so any positive prediction against an actual 0 scores 200;
MAE/RMSE are the meaningful numbers.

### Peak hour — circular metrics

| operator | exact | within-1 (circular) | mean circular error (h) |
|---|---|---|---|
| AM | 0.50 | 0.50 | 2.0 |
| EG | 0.00 | 0.00 | 7.0 |
| GE | 0.00 | 0.50 | 6.0 |
| KO | 0.00 | 0.00 | 8.5 |
| MO | 0.00 | 0.00 | 2.5 |
| NAO | 0.00 | 0.50 | 5.0 |
| NO | 0.00 | 0.00 | 5.0 |
| OO | 0.50 | 0.50 | 1.5 |

Macro exact **0.125**, within-1 **0.25**, mean circular error **4.7 h**. The
output is an honest integer scored with the right (circular) metric; the sample
is far too sparse for the result itself to mean anything.

### Bottom line

The integration is correct, reproducible and honest. **On this ~2-week sample
the models sit right on top of a per-station / per-day mean** — the expected
outcome, stated in the UI next to every forecast.

## 7. Artifacts, provenance and metadata

```
back-end/ml/artifacts/v2/
  index.json                    every artifact + its headline sanity-check metric
  volume/<OP>.joblib  (+ .json) VolumeModel bundle (+ human-readable sidecar)
  peak/<OP>.joblib    (+ .json) PeakModel bundle
```

Each bundle is `{schema_version, pipeline, meta}`. `meta` records (enforced by
`build_meta`, checked in `ml.tests`): model_type, task, operator, target,
feature_names, training_data_source, train/val/test date ranges, row counts
(incl. target zero fraction), random_seed, library_versions,
validation-sanity-check metrics, baseline metrics, rolling-origin sanity, notes,
and a **`provenance`** block:

| provenance field | what |
|---|---|
| `code_sha256` | SHA-256 over the source modules that determine an artifact's behaviour (`dataset.py`, `features.py`, `splits.py`, `model_*.py`, `train_all.py`, …) |
| `data_sha256` | `{passages_csv, tolls_csv}` — SHA-256 of each committed dataset file |
| `git` | `{commit, dirty}` — short hash + whether the tree was modified |
| `library_versions`, `created_at` | interpreter + library versions; UTC timestamp |

So a released artifact identifies exactly which source and which dataset produced
it. `ml.tests` verifies the recorded `data_sha256` still matches the committed
dataset.

`load_bundle` **refuses**:

* a bundle whose `schema_version` major ≠ this build's (`2`);
* a bundle whose recorded `scikit_learn` / `numpy` version ≠ the running
  interpreter's;

…with a clear message and no filesystem path. Determinism: retraining +
re-evaluating produces **identical test metrics** (verified); the `.joblib` bytes
differ only in the `created_at` provenance field.

Total artifact size: **~1.3 MB** (16 bundles) — each file is a complete,
self-describing model. The `models_passages/` + `models_peak_hours/` legacy
`.pkl` (~another few MB) stay until v2 is accepted, then should be deleted.

## 8. Reproducible commands

All run in the pinned container (`app` image — identical scikit-learn as
request-path inference). A dedicated `ml` compose service wraps it:

```bash
docker compose --profile ml run --rm ml -m ml.validate_data     # audit data + lineage
docker compose --profile ml run --rm ml -m ml.evaluate_legacy   # record the old approach's behaviour
docker compose --profile ml run --rm ml -m ml.train_all         # (re)train v2, deterministically
docker compose --profile ml run --rm ml -m ml.evaluate_all      # held-out eval, rerun unchanged
docker compose --profile ml run --rm ml -m ml.smoke_test        # load every artifact + infer
docker compose --profile ml run --rm ml -m ml.tests             # the ML test suite (31 tests)
```

No untracked local Python packages; no host interpreter (the host's is broken —
this is why everything runs in the container).

**Replacing the model.** To serve a client model or a model trained on real
client data: put the client's data in `ml/data/`, run `ml.train_all`
(or drop a bundle that satisfies the `{schema_version, pipeline, meta}` contract
into `ml/artifacts/<version>/`), run `ml.evaluate_all` and `ml.smoke_test`. The
API, the controllers and the frontend are unchanged.

## 9. API behaviour

`/api/forecast/:operator/:YYYYMMDD` and
`/api/peak_hour/:operator/:YYYYMMDD/:YYYYMMDD` call `python -m ml.infer`, which
**only loads committed artifacts — it never trains**. The controllers:

* validate the operator (404 `UNKNOWN_OPERATOR` if it has no stations) and the
  date format (400 `BAD_DATE` / `BAD_RANGE`);
* return 503 `MODEL_UNAVAILABLE` if an artifact is missing or version-incompatible;
* return finite, non-negative volume predictions and integer (0–23) peak hours;
* add to every response: `model` (artifact version, training range, **provenance
  hashes**, a `replaceable` note), `evaluation` (this operator's held-out error
  and the sanity-check baseline — no "beats" verdict), `date_context`
  (`extrapolation: true` when a requested date is outside the ~2-week observed
  window, with the held-out dates named as the safe default), and `limitations`;
  existing fields (`predictions`, per-record `passage_date` / `predicted_hour`)
  are kept;
* never expose a filesystem path or a stack trace.

The `POST /api/training` endpoint is unchanged: **admin-only** and gated by
`DISABLE_DESTRUCTIVE_OPS` (403 `DEMO_MODE_RESTRICTION` for everyone else), so a
public/demo request can never trigger training. It still drives the *legacy*
scripts and is a cleanup candidate (`docs/TECH_DEBT.md`).

## 10. Frontend

The Forecast page (not redesigned) frames the feature as an **integration demo**:

* the disclosure explains it is a replaceable integration, that the baselines are
  sanity checks, and that a client model / client data drops into the same layer;
* the default demo uses the **held-out test dates** (2022-01-13 / 14), not a date
  months outside the sample; dates outside the observed window render an
  **extrapolation warning**;
* each result shows the artifact version, a short code hash, the held-out error,
  and the sanity-check baseline — sourced from the API response, so the copy
  always matches the measured numbers; no metric without its unit and split.

The Project page has a "Replaceable ML integration" section making the same point.

## 11. Remaining limitations

1. **~2 weeks / 15 dates / 1 002 passages.** Test = 2 dates. No modelling makes
   this predictive; only more real data would.
2. Peak-hour observed peaks cluster at 00:00 – 02:00 (sample-generation
   artefact); the feature is a methodology demonstration only.
3. GE has 14 passages total — its models are placeholders.
4. `POST /api/training` still runs the legacy scripts (admin-only, gated).
5. Legacy `.pkl` files, legacy `ml/train*.py` / `ml/predict*.py`, and the tracked
   orphaned dirs (`ml/training_data*/`, `ml/input*/`, `ml/results*/`,
   `models_passages/`, `models_peak_hours/`) should be removed once v2 is
   accepted.
6. `matplotlib==3.9.4` added to `requirements.txt` for evaluation plots — not
   imported by request-path inference.
7. The debt-optimization algorithm was **not** touched by this milestone.
8. sMAPE is reported but uninformative for the zero-inflated volume target.
